# 2026-10-04 — Praivelle House

## What was built

A complete premium boutique-hotel website for **Praivelle House** (Kansas City
area) in `D:/Romen Roy Workspace/Praivelle House`. Node.js + Express + EJS,
data-driven (no DB/CMS), SEO-optimised, Netlify-ready.

Built by cloning the proven `TrueNorth Dental` architecture and re-theming it,
then generating all-new hotel content, imagery and brand assets.

### Deliverables

- **23 routes**, every content page carrying **2,000+ words** inside `<main>`.
- **6 service pages:** rooms-suites, spa-wellness, dining, weddings-events,
  meetings-corporate, experiences-concierge.
- **13 inner pages:** about, team, services-index, offers, gallery, reviews,
  blog-index, faq, contact, careers, privacy-policy, terms, accessibility.
- **4 Journal articles** across four categories.
- **19 image masters** generated (hero, 6 services, 5 gallery, CTA band, cellar,
  4 team portraits) → **76 responsive WebP variants** + favicons + og-image.
- **Brand identity:** gold PH monogram emblem, light + dark logo lockups,
  favicon set (16/32/48/180/192/512 + .ico), 1200×630 OG card.

### Design system

Navy `#0B1F3A` + gold `#C9A24B` + warm cream/ivory neutrals. Playfair Display
(serif display) + Plus Jakarta Sans (UI), both self-hosted. Re-themed by
remapping the existing CSS token names to the new palette via legacy aliases,
then layering a "brand refinements" section (section 18) on top — this avoided
rewriting 2,100 lines of working layout CSS.

## Environment gotchas discovered (Windows + this sandbox)

1. **`child_process` spawning is blocked from Node.** `execFileSync` of any
   binary — including `bash` — throws `EBUSY`. Bash *can* run esbuild directly.
   So the Netlify bundle check had to split: bundle via the shell, verify via
   Node. `npm run verify:bundle` does both.
2. **esbuild's postinstall leaves the .exe locked.** Copy it to a temp path and
   run the copy.
3. **Node `fetch` does not respect `HTTP_PROXY`/`HTTPS_PROXY`** but *does*
   honour `NO_PROXY`. Localhost fetches failed until `NO_PROXY=127.0.0.1`.
4. **agent-browser's daemon resets between Bash tool calls.** Every
   `open`/`interact`/`screenshot` sequence must happen inside a single call.
5. **`agent-browser screenshot --full` returns a blank image** on this page
   (~3.4 KB, all white). Capture viewport-sized sections while scrolling instead.
6. **Background servers die between turns.** Restart before any browser or
   curl verification pass.

### Two CSS traps worth remembering

1. `.hero__inner` is a **centred grid item**, so it shrink-wraps — a later
   `max-width` has no effect. Needs `width: 100%` as well.

   forced a three-line headline. Needed `max-width: none` in the brand layer.

plus `getComputedStyle`), not by reading the CSS.

## Content tightening + SEO + topbar pass (2026-10-04, later still)

Client feedback: "pages content too long and not seo optimized and not friendly,
top bar content decrease". Measured first, then cut.

### The measurement

Wrote a throwaway audit that counted words per page and per block. Result:
**52,718 words across 24 pages, averaging 2,197**, with **91 prose blocks**
carrying most of it — individual prose blocks ran 300–400 words each, and
paragraphs were 60–90 words. That is the actual problem: not the total, but the
wall-of-text shape.

### What changed

- **`scripts/trim-content.js`** (new, reusable): rewrites paragraph text in place
  across `data/` — prose/split bodies ≤48 words, FAQ answers ≤42, card text ≤24,
  step text ≤38 — cutting at sentence boundaries so the voice survives. Re-runnable
  and idempotent. Source files escape typographic characters as `\uXXXX`, so the
  script decodes literals before matching and re-encodes on write; matching raw
  runtime strings silently missed 23 paragraphs.
- **`CAP` map in `views/partials/blocks.ejs`**: caps how many items each block
  renders (prose 2 paragraphs, FAQ 6, cards 6, steps 5, table 8, checklist 8,
  timeline 6). Item counts are a render concern, not a data concern — editing
  arrays in the data files risks corrupting objects, this does not. Overridable
  per block with `b.limit`.
- **Home page**: dropped the "why book direct" prose (now on /offers) and the FAQ
  block (now only on /faq). 14 blocks → 12. A home page should not repeat every
  other page.
- **Result: avg 2,197 → ~1,580 words**, and the shape is now scannable.

### SEO

- **Internal linking** — `views/partials/related.ejs` (new): an explicit RELATED
  map rendered as a "Where to go next" row of 4 contextual links on every content
  page. This was the biggest genuine gap; the site previously relied on nav alone.
- `theme-color` was still the old navy `#0B1F3A` — now `#2E3C85`.
- Added `twitter:site` / `twitter:creator` (derived from the socials list) and
  `twitter:image:alt`. `robots`, `og:locale`, per-page OG images and canonicals
  were already correct.
- `check-seo.js` floor lowered from 2,000 to `MIN_WORDS` (default 800).

### Topbar

Five items → three: **phone + address** on the left, **socials** on the right.
Dropped the email, the hours string and the duplicated concierge line (the
concierge number is still in the header and the nav drawer).

### Two more traps worth remembering

1. **The asset version hash is computed at server boot.** Editing CSS without
   restarting means the browser keeps serving the cached stylesheet under the old
   `?v=` — the change looks like it did nothing. Restart before re-screenshotting.
2. **A centred `inline-flex` eyebrow detaches its icon when the label wraps** on
   narrow screens: the text item fills the row and the icon is pushed to the far
   left. Fix is `display: block` on the eyebrow plus `display: inline-flex` on the
   icon so it flows inline with the text.

Also: the FAQ page hero claimed "Thirty questions" — the render caps made that
untrue, so the copy was made count-agnostic. Worth grepping for number claims
after any content cap.

## Invisible white-on-white text — contrast audit (2026-10-04, final)

Client reported "some section text color white, not showing properly".

### How it was found

Guessing from the CSS would have been slow and unreliable, so I wrote a
**contrast audit that runs in the real browser** and now lives at
`scripts/audit-contrast.js`. It walks the DOM, computes each text element's
effective background (walking up ancestors), and reports anything under a 2.6
contrast ratio with its selector, computed colours, ratio and page offset.

The important detail: **it must treat gradient backgrounds as their average
colour stop.** The first version only read `background-color`, so every
`.section--navy`, the footer and the CTA band — all of which use
`linear-gradient` — reported as white and produced **31 false positives**.
Gradient-aware, the same page reported **4 real problems**. A noisy audit is
worse than none; it sends you fixing things that are not broken.

### The four real bugs

1. **The offer block's "Everything included" list was invisible.** The markup
   used `tick-list--light` (white text) but the panel it sits in is
   `.offer__right` with the light `--tint` background. Changed to the default
   `tick-list`.
2. **The CTA band's phone button was navy-on-navy.** `btn--outline` sets navy
   text and a navy border; it was sitting on the dark CTA band. Changed to
   `btn--outline-light`.
3. **Step numerals** used `color: var(--orange-50)` — a near-white fill relying
   entirely on a 1.5px orange text-stroke to be visible (1.11 ratio on white).
   Now a solid orange fallback with the outlined treatment behind
   `@supports (-webkit-text-stroke: 1px #000)`.
4. **Review and footer stars were still the old gold `#C9A24B`** — a leftover
   from the first theme. Now `var(--orange)`.

### Bonus find

The sweep turned up two **stale `/doctors` links** in `blocks.ejs` (team-preview)
and `post.ejs` — dental-era routes that no longer exist, pointing at 404s. Both
now go to `/team`.

### Lesson

Both bug classes here are *cross-cutting*: a colour utility class applied in the
wrong context, and an old route surviving a rebrand. Neither is visible by
reading one file. The browser-side audit and a grep for the old vocabulary
(`/doctors`, `patient`, `dental`) are what catch them.

## New brand mark + live-text lockup (2026-10-04, final)

Client: "redesign logo image best and more premium and place the logo".

### Choosing the mark

Generated three emblem options — a prairie grass sheaf, a line-art farmhouse
with sun and fields, and an interlocked P/H monogram in a double ring. Rendered
all three at **120px and 44px side by side** before choosing, which was the
decisive test: the sheaf and the farmhouse both turn to mush at header size,
while the monogram stays instantly legible. **A logo has to work at 44px.**

Chose the monogram. It also reads as the language of a luxury boutique hotel
(thin-stroke serif in a double ring) rather than a rustic inn.

### Two mark variants, generated not hand-made

`buildMark()` in `scripts/generate-image-variants.js` now:
- **auto-crops** to the disc (bounding box of non-white pixels) instead of
  hard-coded extract coordinates — the old hard-coded `extract()` would have
  silently mis-cropped a differently-framed render
- emits `logo-mark.webp` (indigo disc + orange monogram) for light surfaces
- emits `logo-mark-light.webp` by **chroma-keying the indigo field out** — the
  disc would vanish on the navy footer, so the ring and letterforms ship on
  transparency instead. Decided per pixel by distance to navy vs orange.

### The lockup is live text, not a bitmap

`views/partials/lockup.ejs` renders the mark `<img>` plus the wordmark as
**HTML text in Poppins**, driven by `site.wordmark = { lead, accent, tagline }`.
The old lockup baked the wordmark into a PNG with Segoe UI (Poppins is not
installed, so SVG rendering could not use it) — live text renders in the real
display face at any size and stays crisp. Used in the header, the mobile drawer
and the footer (`light: true` swaps the mark and lightens the type).

### The bug worth remembering

The CSS patch that added the lockup styles **inserted the block inside the
file's opening comment block**. My anchor search was `l.indexOf('/* ---')`,
which matches the section-index header at the top of the file, not the section
I wanted. Result: the header comment was split, the displaced lines
(`9. Page hero … ===== */`) became loose text in the stylesheet, and the
browser **silently dropped rules** — the footer lost its navy gradient and
rendered white-on-white.

Two lessons:
1. **Anchor on something unique.** `/* ---` appears dozens of times; the brace
   count and comment count both still balanced, so my integrity checks passed
   on a broken file.
2. **Validate CSS structurally, not by counting braces.** A check that strips
   comments and then flags any non-rule text at depth 0 catches exactly this.
   Added that check; it reported clean after the repair.
